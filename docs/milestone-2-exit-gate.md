## Authentication and architecture

- `packages/database/prisma/migrations/0002_auth_identity` defines the unique provider/provider-account mapping to a canonical User. The auth repository provisions user and identity atomically, with `America/Toronto` initial timezone; its uniqueness fallback returns the winning account when first sign-ins race. User deletion removes identity rows without making an identity deletion cascade into academic data. `tests/integration/auth-identity.test.mjs` and `auth-callbacks.test.mjs` exercise repeat sign-in and callback semantics. This audit also called the production identity repository concurrently from separate database clients on the disposable Neon database: both calls and a repeat returned one canonical User ID; SQL counted one identity and one User. The synthetic rows were deleted afterward.
- `apps/web/src/server/auth.ts` configures NextAuth.js with Google alone, JWT sessions, server-side actor lookup, and OIDC `openid` login scope. The Google subject is the durable mapping key, not email or name. Tokens and Google credentials are neither persisted for login nor added to the exposed canonical actor. Deleting the User invalidates subsequent actor lookup. The real Google OAuth round trip has not been exercised here; the provider/callback boundary is mocked in local tests.
- The server application composition root consumes the public database contract. `scripts/check-package-boundaries.mjs` rejects transport imports of Prisma, database internals and repository operations. Domain and planner-core remain independent of database/Auth.js/web. No application service takes a client-supplied authoritative `userId`.
- Representative Next.js handlers cover term CRUD/archive, course and task create/list, task read/update/archive, availability reads/create and authenticated account export. `apps/web/src/server/transport.ts` applies bounded JSON and same-origin checks and converts structured service results to safe, no-store HTTP responses. Actual handlers passed the guarded live route/service/PostgreSQL test; Chromium E2E separately passed against the booted Next.js app. An external Google redirect and combined browser/Neon session have not been exercised with deployment credentials.
- `apps/web/src/server/monitoring.ts` optionally emits only a fixed internal-failure signal to Sentry, disabled without server-only `SENTRY_DSN` or during tests. It removes request, user, context, exception and breadcrumb fields, without logging academic content or tokens. This fulfills ADR 0001's first trusted-error-boundary wiring, not later observability hardening.

## Validation, errors, concurrency and lifecycle

- `application/validation.ts` and the service-specific strict Zod schemas check IDs, text, calendar dates versus instants, IANA timezone, minute counts, percentage/range bounds, session ordering, recurrence subset and expected versions. Ownership helpers check both roots and nested relations. `application/errors.ts` defines `VALIDATION_ERROR`, `CONFLICT`, `STALE_WRITE`, `NOT_FOUND`, `UNAUTHORIZED`, `EXTERNAL_PROVIDER_FAILURE`, `PLANNER_INFEASIBLE` and private `INTERNAL_ERROR`; known database constraint failures map to safe results. The transport sends code and safe message, never Prisma diagnostics or stack traces.
- ADR 0004 records why `updatedAt` alone is insufficient for compare-and-write. Migration 0003 adds Task version; migrations 0004, 0005 and 0006 add explicit versions across academic, schedule, inbox, work-session and integration records. Repositories condition updates on `(userId, id, version)` and increment on success, producing deterministic stale results. Parent/dependency changes use transaction serialization and version checks. The live term test rejects a stale version and accepts the fresh version; other families retain local simulation coverage.
- `docs/account-data-lifecycle.md` specifies term/course/assessment/task archives, integration disconnect that clears credential references without erasing canonical history, scoped external mapping preservation and explicit atomic account deletion. `accountData.export()` returns `university-planner-canonical` version 1 with owned records; it excludes auth identities and redacts credential references and token/secret keys. The live test exports one actor's records and omits a populated synthetic credential reference, then deletes that actor while preserving the other. A separate live forced deletion failure preserved both the User and dependent term; the following confirmed deletion removed the User. Snapshot isolation and provider-side revocation are deferred.
- Migration chain is `0001_canonical_foundation` (Milestone 1), `0002_auth_identity`, `0003_task_optimistic_version`, `0004_academic_service_versions`, `0005_schedule_state_versions`, `0006_lifecycle_versions`. Migrations 0002–0006 are new for Milestone 2. Prisma deployed all six from an empty disposable database and reported the schema current; this audit reran migration status and a read-only Prisma database-to-schema diff, which reported **No difference detected**. No migration SQL changed.

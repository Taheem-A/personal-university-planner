## Authentication and architecture

- `packages/database/prisma/migrations/0002_auth_identity` defines the unique provider/provider-account mapping to a canonical User. The auth repository provisions user and identity atomically, with `America/Toronto` initial timezone; its uniqueness fallback returns the winning account when first sign-ins race. User deletion removes identity rows without making an identity deletion cascade into academic data. `tests/integration/auth-identity.test.mjs` and `auth-callbacks.test.mjs` exercise uniqueness, repeat sign-in, and deletion/callback semantics through simulated boundaries; clean live migration and concurrent callback proof remain pending.
- `apps/web/src/server/auth.ts` configures NextAuth.js with Google alone, JWT sessions, server-side actor lookup, and OIDC `openid` login scope. The Google subject is the durable mapping key, not email or name. Tokens and Google credentials are neither persisted for login nor added to the exposed canonical actor. Deleting the User invalidates subsequent actor lookup. The real Google OAuth round trip has not been exercised here; the provider/callback boundary is mocked in local tests.
- The server application composition root consumes the public database contract. `scripts/check-package-boundaries.mjs` rejects transport imports of Prisma, database internals and repository operations. Domain and planner-core remain independent of database/Auth.js/web. No application service takes a client-supplied authoritative `userId`.
- Representative Next.js handlers cover term CRUD/archive, course and task create/list, task read/update/archive, availability reads/create and authenticated account export. `apps/web/src/server/transport.ts` applies bounded JSON and same-origin checks and converts structured service results to safe, no-store HTTP responses. Route simulation exercises these actual handlers; the browser/real Next.js/PostgreSQL path has not passed.
- `apps/web/src/server/monitoring.ts` optionally emits only a fixed internal-failure signal to Sentry, disabled without server-only `SENTRY_DSN` or during tests. It removes request, user, context, exception and breadcrumb fields, without logging academic content or tokens. This fulfills ADR 0001's first trusted-error-boundary wiring, not later observability hardening.

## Validation, errors, concurrency and lifecycle

- `application/validation.ts` and the service-specific strict Zod schemas check IDs, text, calendar dates versus instants, IANA timezone, minute counts, percentage/range bounds, session ordering, recurrence subset and expected versions. Ownership helpers check both roots and nested relations. `application/errors.ts` defines `VALIDATION_ERROR`, `CONFLICT`, `STALE_WRITE`, `NOT_FOUND`, `UNAUTHORIZED`, `EXTERNAL_PROVIDER_FAILURE`, `PLANNER_INFEASIBLE` and private `INTERNAL_ERROR`; known database constraint failures map to safe results. The transport sends code and safe message, never Prisma diagnostics or stack traces.
- ADR 0004 records why `updatedAt` alone is insufficient for compare-and-write. Migration 0003 adds Task version; migrations 0004, 0005 and 0006 add explicit versions across academic, schedule, inbox, work-session and integration records. Repositories condition updates on `(userId, id, version)` and increment on success, producing deterministic stale results. Parent/dependency changes use transaction serialization and version checks. Local stale/fresh tests pass; live concurrent-state checks remain pending.
- `docs/account-data-lifecycle.md` specifies term/course/assessment/task archives, integration disconnect that clears credential references without erasing canonical history, scoped external mapping preservation and explicit atomic account deletion. `accountData.export()` returns `university-planner-canonical` version 1 with owned records; it excludes auth identities and redacts credential references and token/secret keys. Snapshot isolation and provider-side revocation are deferred. A disposable live account deletion and forced rollback are mandatory before exposing a deletion endpoint.
- Migration chain is `0001_canonical_foundation` (Milestone 1), `0002_auth_identity`, `0003_task_optimistic_version`, `0004_academic_service_versions`, `0005_schedule_state_versions`, `0006_lifecycle_versions`. Migrations 0002–0006 are new for Milestone 2. Source checks and Prisma schema validation pass, but **Prisma migrate deploy/status from zero through 0006 on a fresh disposable database have not been performed in this audit**. Earlier isolated SQL checks only covered 0001–0003 and do not prove current Prisma migration history.

## Verification ledger and blockers

- Local `pnpm verify`: formatting, lint, package boundaries (59 source files), Prisma client generation and schema validation, strict TypeScript, 23/23 unit tests, 35/35 integration tests, and core/database/Next.js production builds passed. Its final Playwright stage failed: both browser tests could not launch because Chromium is absent. The browser executable download returned truncated archives on repeated attempts. `pnpm check:dependencies` reported **no known vulnerabilities**. Local Node 24.19.0/pnpm 11.19.0 also produce engine warnings against the pinned Node 24.21.0/pnpm 12.5.1 toolchain; the green earlier stages do not replace a supported-toolchain CI run.
- `tests/database/services.integration.mjs` is a guarded actual-route → service → transaction → Prisma → PostgreSQL proof. It requires `APP_ENV=test`, an unmistakable `up_m2_service_*` direct Neon URL in `SERVICE_TEST_DATABASE_URL`, exact confirmation `RUN_M2_SERVICE_TESTS`, and prior migration deployment. The URL is unavailable in this workspace, so the test is **not passed**.
- Playwright Chromium is not installed in this workspace. Its attempted download returned truncated archives. `pnpm verify` can complete earlier steps but cannot pass browser E2E here; CI has not supplied an independent green Milestone-2 run.
- No real Google callback has been exercised against a test OAuth client. The mocked Auth.js boundary tests are valuable but do not assert external OAuth availability. The product gate's primary blocker is still database, migration and browser/CI evidence.
